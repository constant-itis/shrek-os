# Dogfood-0 — boot the sealed image interactively and do real work in it

**Status:** OPEN (2026-08-21). Backend/security feature development is **frozen for the duration** of
this track (see §Parked). Dogfood-0 is a desktop/integration track: take the artifacts we already
build (sealed dm-verity image + `shrek-desktop` sysext + the read-only Work-drawer wiring) and make
them into a machine the owner can sit down at and develop on.

## Goal (acceptance)
Boot the **real sealed image** interactively as a usable dev box, and prove one real coding workload
appears **live** in the Work drawer:

> Inside the VM, check out shrek-os, edit it, run `cargo check`/`cargo test`, and run one
> `shrek run -- cargo test` session that shows up as a live row in the Quickshell Work drawer.

If that works end-to-end, Dogfood-0 is done. The next dogfood case (out of scope here) is a real
brokered coding-agent session (model egress via the broker) against the same checkout.

## Decisions (locked with the owner 2026-08-21)
- **The libvirt domain is the authoritative, reproducible VM definition** — generated by a script from
  fixed image/layer/firmware/device assumptions. virt-manager is only the GUI onto that domain; any
  manual tweak in virt-manager is **non-authoritative** and must be folded back into the generated
  config if it turns out to be required. This is the owner's persistent day-to-day Dogfood VM.
- **`scripts/dogfood-vm.sh` is a disposable headless acceptance oracle** using the *same* image, layer
  store, firmware, and virtual devices as the libvirt domain — it exists to prove the Work-drawer
  acceptance reproducibly (CI-style), not for daily use.
- **First workload = ordinary development of shrek-os itself.** `shrek-dev` carries the **minimum
  toolchain that this workload empirically needs**, nothing more. Full mkosi/image-construction inside
  the VM is explicitly **not** required for Dogfood-0.
- **Persistence is done properly:** `/usr` stays sealed/read-only (dm-verity); writable `/home` (and
  persistent `/var`) live on a **separate writable data disk**. We do *not* make root writable — that
  would defeat the immutable model. This realizes the previously-deferred "sealed-/usr + writable-/"
  state model, in-scope because a "normal development session" requires persistence.

## The four gaps between "headless CI gate" and "usable dev box"
Today `scripts/boot-vm.sh` boots the raw headless (`-display none -serial file`), throwaway OVMF vars,
volatile state; `shrek-desktop` is `exec sway -c … → exec quickshell` with **no login flow** and a
**headless WLR backend**. Dogfood-0 closes:

1. **Graphical + interactive boot.** virtio-gpu (+virgl) display over SPICE, virtio keyboard/tablet
   input, and a **login/session**: getty **autologin** on a VT → `shrek-desktop` running Sway on the
   real **DRM/KMS** backend (drop the smoke's `WLR_BACKENDS=headless`/pixman/software env). Seat via
   `seatd`/libseat. (greetd/UWSM display-manager flow is a later refinement, not Dogfood-0.)
2. **Persistence.** A second writable disk (GPT, own filesystem) providing persistent `/home` and
   `/var`; mounted early (fstab/mount units baked into sealed `/usr`), surviving reboot **and** image
   A/B updates (data disk is never part of the sealed image). OVMF **nvram persists** so the enrolled
   Secure Boot keys survive across boots (first boot = SETUP MODE blank vars → systemd-boot
   auto-enrolls → persisted thereafter).
3. **Normal desktop services/settings.** Whatever a normal interactive Debian session needs and the
   headless smoke didn't: `systemd-logind` + seat, `systemd-networkd`/resolved (or NM) for real net,
   `dbus`, time sync, fonts, PipeWire/WirePlumber for audio, XKB/keymap, locale. Enumerate empirically
   from a first interactive boot; bake the required units/settings into the sealed base or the desktop
   layer.
4. **`shrek-dev` extension + live Work-drawer proof.** A signed `shrek-dev` sysext (same pattern as
   `shrek-desktop`: `layers/shrek-dev/`, `Format=sysext` + `Packages=`, base-tree+overlay per the
   mkosi packaged-sysext gotchas) carrying the **minimum** toolchain (§shrek-dev). Then run
   `shrek run -- cargo test` on an in-VM checkout → gatekeeperd writes the `shrek-session/1` record →
   the real `SessionProvider` renders a live row in the Work drawer. That render is the acceptance.

## shrek-dev — minimum toolchain (empirically derived, not a wishlist)
Derived from what building this workspace actually requires (verified 2026-08-21):
- **Rust toolchain**, version-pinned to the workspace (currently **1.95.0**) — reproducible, not
  "whatever's latest".
- **A C toolchain**: `cc`/gcc + `binutils` + libc headers (`build-essential` equivalent). Required
  because the workspace compiles C at build time — `rusqlite` is `features=["bundled"]` (builds SQLite
  from source via the `cc` crate → `libsqlite3-sys`) and `ring` compiles C/asm.
- **`pkg-config`**, **`git`**, and **one editor** (owner's pick; default a terminal editor to keep the
  closure small).
- Explicitly **excluded** from Dogfood-0: mkosi/qemu/docker (image construction), heavy IDEs. Add only
  if a later dogfood workload empirically needs them.

The toolchain manifest is **inventory-derived from the owner's actual workstation** (beepboop) so the
layer reflects real usage, then **pinned** so the layer is reproducible.

## Milestones (in order)
- **M0 — Interactive graphical boot of the *current* sealed image.** Gaps #1 (graphics + input +
  autologin DRM session) + persistent OVMF nvram. Result: owner sits at the Sway/Quickshell desktop in
  virt-manager. (Answers "I just want to see it run.") No shrek-dev, no persistence disk yet.
- **M1 — Persistence + normal desktop services.** Gaps #2 + #3. Reboot-survivable `/home`+`/var`; a
  normal session (net, audio, fonts, logind/seat). Editing files in the VM now sticks.
- **M2 — `shrek-dev` layer.** Gap #4a. Inventory→pin→signed sysext→sealed-enable. Prove `cargo
  check`/`cargo test` of a shrek-os checkout runs inside the VM.
- **M3 — Live Work-drawer proof.** Gap #4b. `shrek run -- cargo test` → live row in the Work drawer;
  `scripts/dogfood-vm.sh` asserts it headless/reproducibly. **= Dogfood-0 acceptance.**

## M0 implementation (as built)
- **Autologin:** `mkosi.conf` `Autologin=yes` → root tty1 autologin via `agetty → /bin/login → PAM`;
  `libpam-systemd` in the base registers a real **logind session on seat0** (the seat sway's
  `libseat→logind` backend uses — no `seatd`). Root session for M0; a non-root `dev` user lands with the
  M1 persistence disk (its home needs writable `/home`).
- **Session start:** `/etc/profile.d/zz-shrek-desktop.sh` execs `shrek-desktop` on `XDG_VTNR=1`, **guarded
  on `/dev/dri/card0`** so it fires only on the graphical dogfood VM — never the headless CI serial gate
  (std-vga, no DRM). Renders with `WLR_RENDERER=pixman` (software on the VM's virtio-gpu; works with or
  without host virgl — M1 flips to GLES when accelerated). Desktop layer gains `libseat1` + `xkb-data`.
- **Stays up:** `DOGFOOD=1 scripts/build-in-container.sh` masks the self-poweroff spike gates
  (`shrek-mount-gate` owns `poweroff-force`, `shrek-desktop-gate` is the redundant headless proof) via
  `/etc/systemd/system/<unit>→/dev/null`. Masks are gitignored + removed on a normal build → the CI image
  and `desktop-sealed-proof.sh` are byte-unchanged (the headless gate is preserved).
- **Verification:** `scripts/dogfood-vm.sh` (headless oracle) boots the DOGFOOD image graphically under
  qemu+virtio-vga and `screendump`s the guest scanout to PNG — the screenshots are the M0 evidence.
  `scripts/dogfood-libvirt.sh` generates the persistent-NVRAM daily-driver domain (SPICE + virtio input +
  virgl-when-supported) — the authoritative reproducible config virt-manager imports.
- **Build order:** `scripts/build-desktop-layer.sh` → `DOGFOOD=1 scripts/build-in-container.sh 1` →
  `scripts/build-layers.sh desktop` → `scripts/dogfood-vm.sh`.

## Parked (do NOT build unless Dogfood-0 exposes it as a concrete blocker)
Authority-mutation UX (grant/stop/promote), SAK/VT trusted path, SWAMP-5 (hybrid reranking), PN1
writable-grant write-back. If dogfooding forces one open, that's the documented exception — surface it,
don't silently start it. The Work drawer stays **read-only/display** throughout.

## Method (unchanged)
Design-first on the slow VM loop (research lookupable facts, don't guess-and-check); reproducible libvirt
domain + headless oracle share assumptions; owner-split commits (provider-neutral tree); push
constant-itis; `system-index refresh --graphify` + baseline bump per landing.
